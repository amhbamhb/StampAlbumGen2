Download Verification

Back to home

If you want users to feel secure about a downloaded binary, CRC is not the right primary tool. The best practical baseline for public downloads is a cryptographic hash plus a digital signature.

For this project, the recommended release pattern is:

  1. Publish the Linux and Windows binaries.
  2. Publish a SHA256SUMS.txt file listing the SHA-256 hash for each artifact.
  3. Publish a detached signature for that checksum file.
  4. Publish the public verification key on the website and keep the private signing key offline.

Published Checksum Files

Current release checksum files are published directly on this site:

  • stamp_album_gen2.sha256
  • stamp_album_gen2.exe.sha256
  • SHA256SUMS.txt
  • CRC32SUMS.txt

Expected artifacts in those files:

  • stamp_album_gen2 (Linux)
  • stamp_album_gen2.exe (Windows)

What To Use

Best usable default: SHA-256 checksums plus a detached signature created with minisign.

Why this combination works well:

  • SHA-256 tells the user whether the file they downloaded matches the file you released.
  • A digital signature tells the user the checksum list really came from you, not from an attacker who replaced both the binary and the hash file.
  • Minisign is simpler for many end users than a full GPG workflow, while still providing strong authenticity checks.

Windows-specific extra layer: if possible, also sign the Windows executable or installer with Authenticode. That improves the Windows trust experience, but it should complement signed checksums, not replace them.

Why CRC Is Not Enough

CRC is useful for detecting accidental corruption such as a damaged transfer or storage error. It is not designed to resist intentional tampering.

If an attacker can replace the binary, they can also replace a CRC value. That is why public software distribution should use cryptographic hashes and signatures instead.

The important trust rule is this: sign the checksum manifest, then ask users to verify the signature and the file hash.

Linux Example

Most common check with a per-file checksum:

sha256sum -c stamp_album_gen2.sha256

Alternative check with the combined manifest:

minisign -Vm SHA256SUMS.txt -P "YOUR_PUBLIC_KEY_HERE"
sha256sum -c SHA256SUMS.txt --ignore-missing

The first command verifies authenticity. The second confirms that the downloaded binary matches the published SHA-256 value.

Optional CRC check for accidental transfer errors:

cksum stamp_album_gen2
cat CRC32SUMS.txt

Compare the CRC32 number and byte length from cksum against the stamp_album_gen2 line in CRC32SUMS.txt.

Windows Example

Most common check with a per-file checksum:

Get-FileHash .\stamp_album_gen2.exe -Algorithm SHA256

Compare the hash to the value in stamp_album_gen2.exe.sha256.

On Windows, verify the signature with minisign and compare the SHA-256 hash with PowerShell:

minisign -Vm SHA256SUMS.txt -P "YOUR_PUBLIC_KEY_HERE"
Get-FileHash .\stamp_album_gen2.exe -Algorithm SHA256

Then compare the reported SHA-256 value with the stamp_album_gen2.exe line in SHA256SUMS.txt.

Optional CRC check on Windows with 7-Zip installed:

7z h -scrcCRC32 .\stamp_album_gen2.exe

Compare that CRC32 result with the stamp_album_gen2.exe line in CRC32SUMS.txt.

Best-Practice Summary

  1. Do not rely on CRC as the main trust mechanism.
  2. Use SHA-256 for integrity.
  3. Use a detached digital signature for authenticity.
  4. Keep the signing key offline and publish the public key clearly on the website.
  5. Add Authenticode for Windows when practical.

This gives users a verification path that is strong, understandable, and realistic to use on both Linux and Windows.
